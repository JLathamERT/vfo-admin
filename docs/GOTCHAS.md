>
> **Numbers are permanent.** Gotchas are referenced as `#N` from `SESSION_REFERENCE.md`, the operator prompts, and across `docs/` — **NEVER renumber.** Add new gotchas to the END of this list, incrementing from the current max (#188).

**1. pg_cron auth uses the NEW `sb_secret_xxx` key, not the legacy `eyJ` JWT.**
When writing a pg_cron job that POSTs to the function URL with Authorization: Bearer <key>, use the value from "Publishable and secret API keys" tab in Supabase Dashboard. The function's SUPABASE_SERVICE_ROLE_KEY env var maps to that newer key, NOT the legacy service_role JWT. Both look similar; the wrong one returns 401.

**2. Test a cron immediately by EXECUTE-ing its stored command.**
No need to wait for the schedule:

```sql
DO $$
DECLARE cmd text;
BEGIN
  SELECT command INTO cmd FROM cron.job WHERE jobname = '<JOBNAME>';
  EXECUTE cmd;
END $$;
```

Then poll `net._http_response` ~10s later. The key never leaves Postgres.

**3. PowerShell here-string commit messages break on apostrophes.** Use `git commit -F <tmpfile>` instead of `git commit -m @'...'@`. The @'..'@ closing token parses incorrectly when the body has straight apostrophes, splitting your message across multiple pathspec args. The Bash tool's `cat > file << 'EOF' ... EOF` heredoc is cleaner if you're already operating in a Bash context.

**4. Stripe Connect transfers fail with `insufficient_capabilities_for_transfer`** if the destination account lacks the `transfers` capability — common in test mode. Verify with `acct.capabilities.transfers === 'active'` on the connect account BEFORE wiring it as `members.stripe_account_id`. Surface failures via admin notifications when relevant; the transfer call itself returns a normal Stripe error body.

**5. All 4 Stripe env vars must point at the same Stripe account in matching modes.** `STRIPE_SECRET_KEY` + `STRIPE_WEBHOOK_SECRET` = live mode of account X; `STRIPE_SECRET_KEY_SANDBOX` + `STRIPE_WEBHOOK_SECRET_SANDBOX` = test mode of account X. If they drift (e.g., sandbox key for account A but sandbox webhook secret for account B, or one secret missing entirely): incoming webhooks 401-silently, and `GET /v1/customers/{id}/payment_methods` for a customer in the "wrong" account returns empty data (handler maps this to `no_payment_method`). Verify with `dashboard.stripe.com/test/customers/<cus_id>` — the URL works for the account the user is currently logged into; "No such customer" means the env points elsewhere.

**6. `recN_status` is now written `'Sent'` by `automation_CONTRACT_invoicereceipt`** (and the tax equivalent writes `rec{N}_status='Sent'` on `client_tax_plans`). AutomationPanel displays NULL as the literal string "pending" via a frontend fallback. New rows get 'Sent' automatically; pre-existing rows that show "pending" despite `recN_email_sent=true` can be backfilled with: `UPDATE pipeline_map1 SET recN_status='Sent' WHERE recN_email_sent=true AND recN_status IS NULL;`

**7. Function-log endpoint only returns HTTP status lines.** The Supabase MCP `get_logs` for `edge-function` shows method/status/timing but NOT the `console.log()` contents from inside handlers. To debug handler behavior, instrument with an extra DB write or inspect `net._http_response` after firing.

**8. PowerShell `git pull | tail -3` silently fails** — `tail` is not a PS cmdlet. The pipeline error can prevent `git pull` from running at all. Use `Select-Object -Last 3` instead, or just omit the pipe.

**9. `pipeline_sandbox_config` must have a row for every pipeline that uses sandbox-aware handlers.** Currently `'MAP 1'`, `'TAX'`, `'ADVISOR_ONBOARDING'`, and `'ACCOUNTANT_ONBOARDING'`. Without the row, handler defaults to live mode and external services (BoldSign, Stripe) get the wrong-mode API keys — webhooks often don't fire, or fire to the wrong account where you can't see them. When adding a new pipeline, INSERT a matching `pipeline_sandbox_config` row before any handler tries to read it. **Exception:** PIP Meetings intentionally reuses the `'MAP 1'` row (rides on Holistic Planning's sandbox toggle) — no separate `'PIP'` row exists.

**10. `boldsign-webhook` deploy requires `--no-verify-jwt` flag every time.** Default Supabase CLI deploy enables JWT verification on the function → BoldSign gets 401 silently and webhook events drop. `config.toml` has `verify_jwt = false` for stickiness, but always pass the flag too — the live registry setting is what matters and the flag overrides it.

**11. Chain auth pattern: forward `body.token`, not just the Authorization header.** The frontend's `callApi()` sends `Authorization: Bearer <SUPABASE_ANON_KEY>` (the anon key, not the admin session token) and puts the admin session token in `body.token`. The auth middleware reads `body.token` for session validation. When one AUTH handler chains to another via HTTP fetch, the chained call's body must include `token: body.token` — forwarding the Authorization header alone leaves the chain with anon-level auth and the chained handler 401s.

**12. MIME headers: never push empty strings for CC/BCC.** When building raw RFC 2822 emails for Gmail's drafts API, the first empty line in the headers block is the header/body separator. Adding an empty `Cc:`/`Bcc:` slot to the headers array causes Gmail to interpret everything from the next line down (Subject, MIME-Version, etc.) as body text. Build conditionally:

```js
const lines = [`To: ${to}`];
if (cc.length) lines.push(`Cc: ${cc.join(", ")}`);
if (bcc.length) lines.push(`Bcc: ${bcc.join(", ")}`);
lines.push(`Subject: ${subj}`, "MIME-Version: 1.0", ...);
```

DO NOT use a `.filter(l => l !== undefined)` that lets empty strings through. **Also avoid em dashes (—) in Gmail Subject headers** — they require RFC 2047 encoding for non-ASCII; without it Gmail renders the subject as mojibake (`â€"`). Use ASCII hyphens (`-`) in subject lines unless you implement the full `=?utf-8?B?<base64>?=` encoder.

**13. Stripe webhook routes by `metadata.pipeline` and `metadata.payment_kind`.** When creating PaymentIntents / Checkout Sessions, set: `metadata.pipeline` to `'MAP 1'`, `'TAX'`, `'ADVISOR_ONBOARDING'`, or `'PIP'`; `metadata.payment_kind` to a domain-specific tag (`'retainer'` for Tax 3, `'implementation'` for Tax 5 off-session charge, `'onboarding'` for advisor onboarding, `'purchase'` for PIP Meetings purchase, or for MAP1 `metadata.payment_number=N`). The webhook handler reads these to decide which table, which column to flip, and which downstream chains to fire. Missing metadata → the webhook falls through to the legacy MAP1 path and may write to the wrong row.

**14. Drive API can't fetch publicly-shared files via OAuth — use Supabase Storage instead.** "Anyone with the link" Drive files return 404 from `drive/v3/files/{id}?alt=media` even with valid OAuth. Either the file must be owned by the OAuth account, or in a Shared Drive with explicit membership. For static public-fetch assets, host them in a public Supabase Storage bucket and fetch the URL directly with no auth — same code, fewer auth hops, works every time.

**15. Stripe idempotency keys must auto-rotate per retry attempt, not be reused.** A key like `tax-impl-{plan_id}-{date}` will collide after a DB state reset because Stripe returns `Keys for idempotent requests can only be used with the same parameters` even though the params look the same to you (Stripe fingerprints the WHOLE request including timestamps inside the request body). Include a suffix that changes naturally when the retry context changes — e.g. embed the prior `payment_intent_id` suffix: `tax-impl-{plan_id}-{retainer_pi_last8}-{date}`. After reset → retainer PI suffix changes → idempotency key changes → Stripe accepts the new charge.

**16. Public chain target with AUTH origin: move to PUBLIC_HANDLERS with internal auth gate.** Pattern: a PUBLIC token-page (e.g. `/tax-postreview-decide`) needs to chain to a handler that was originally admin-only (e.g. refund). Don't try to spoof an admin token from the public side. Instead, move the target handler to `PUBLIC_HANDLERS` and add an inline gate at the top:

```js
const isServiceRole = req.headers.get('Authorization')?.includes(SUPABASE_SERVICE_ROLE_KEY);
const adminSession = await validateAdminSession(body.token);
if (!isServiceRole && !adminSession) return 401;
```

This accepts BOTH service-role bearer (used by the chain) AND admin session token (used by direct admin button clicks), with no behavior change for the latter.

**17. Notification rows use column `message`, not `body`.** The notifications table schema is `(id, recipient, client_id, pipeline, title, message, link, read, dismissible, created_at)`. Handlers that write `body:` silently insert NULL into `message` and the bell shows blank rows. Always use `message`.

**18. Notification `link` must be a real frontend route.** Use `/admin/client/<id>?tab=tax` (or `?tab=automation` for MAP1), NOT `/clients/<id>`. For advisor onboarding (no per-client detail route), use `/admin?tab=advisors&section=advisor_onboarding`. Wrong link → bell click redirects to login (route doesn't exist → auth gate trips). When backfilling old rows: `UPDATE notifications SET link='/admin/client/'||client_id||'?tab=tax' WHERE link LIKE '/clients/%';`

**19. `notifications.dismissible` boolean controls the Done button.** Default `true`. FYI notifications (e.g. "Tax 3 client paid") get `dismissible=true` → bell shows a green Done button that marks read + filters locally. Action-required notifications (e.g. "Tax 3 Yes path — pricing form needed", "Tax 3 ExtraMeeting requested — schedule") get `dismissible=false` → no Done button; they clear only when the admin completes the underlying action (which side-effects an UPDATE on `notifications` to set read=true for all matching rows).

**20. Em dash (—) vs en dash (–) in status_options.** The DB seed had en dash `–` in some status_options rows but the frontend `statusColors` map was keyed on em dash `—`. Status pills rendered grey because the lookup missed. When adding new status values, mirror the EXACT punctuation in BOTH the DB seed AND the frontend color map; prefer em dash consistently.

**21. Linking a client to a program needs BOTH the `clients.enrollment_id` AND a `client_enrollments` join row.** `clients.enrollment_id` is the primary/display enrollment; `client_enrollments(client_id, enrollment_id)` is the M:N join the frontend uses to populate program client lists. Inserting only one of the two means the client won't appear in the program's UI until an admin clicks "Add existing client" (which inserts the missing join row). When creating test fixtures, insert both.

**22. The tax revshare sweep is retry-only.** It picks up plans where `*_rev_share='Pending'` or `*_rev_paid='Failed'` — NOT plans where revshare was never started. Fresh paid plans must reach the Tax 4 admin decision (and then either the 24h Continue auto-lock OR an explicit client click on the Continue green button OR an Undecided→Proceed/Confirmed click) to set `Pending` first. The earlier "never-attempted" branch in the sweep was a latent bug that auto-fired revshare on any paid plan once Tracy's sheet was populated, bypassing the Tax 4 admin decision; the fix removed that branch.

**23. Client-visible tax labels are program-aware via `utils/program-label.ts`.** `programLabel(programId)` returns `"VFO Tax Planning"` for program_id=4 and `"VFO Holistic Planning"` for program_id=1 or NULL legacy. Five call sites (invoice header, invoice footer, retainer-receipt header, implementation-receipt header, Stripe Checkout product name, Stripe off-session implementation charge description, BoldSign agreement title). Internal-only labels (`notifications.pipeline='TAX'`, `email_templates.pipeline='TAX'`, `pipeline_sandbox_config.pipeline='TAX'`) stay program-agnostic — they're lookup keys, not display names. Same idea applies to advisor and PIP — internal `pipeline='ADVISOR_ONBOARDING'` / `pipeline='PIP'` are lookup keys; advisor-facing labels use full plan names ("VFO Fast Track" / "Partnership Fast Track" / "Corporate Membership"), PIP-facing labels use the purchase description ("Tax Planning" or "N Additional PIP Meeting(s)").

**24. `tax_save_deposit_pi` extracts the LAST `pi_...` substring from input.** Defensive against paste-over where the admin doesn't clear the existing value before pasting a new PaymentIntent ID — without this the column ends up containing two concatenated `pi_...` strings and the subsequent refund fails. Also accepts Stripe dashboard URLs containing `/payments/pi_...`.

**25. `pipeline_map1.client_id` is UNIQUE.** Migration `pipeline_map1_unique_client_id` (2026-05-21) added the constraint to prevent the historical drift where stale handler-INSERT branches silently created duplicate rows for the same client. Any code path that tries to insert a second row for an existing client_id now hard-fails with Postgres `23505 unique_violation`. MAP 1 handlers all use `.maybeSingle()` to look up by client_id; legacy "if no row found, INSERT new one" fallback branches in some handlers (notably `pipfu-decision.ts`) are now dead code but harmless. Same audit not yet applied to `client_tax_plans`. `client_priority_tracks` intentionally does NOT have a UNIQUE constraint on `client_id` — clients can have many priority tracks (regular + tax + pip rows distinguished by `track_type`, plus multiple PIP meetings per client).

**26. Tracy's revshare sheet structure (MAP 1 + tax).** Master sheet `1PvUEWwTH70OBHabdHPh2SS9U7isITOzHmSd11GoHGJ0`, Home Page tab: client_ref in column A, hyperlink to a batch sheet in column I. Each batch sheet has tabs named per client last name. Within each batch tab, the revshare handler reads `G7:O200` and matches a row where column I = the receipt number (`rec{N}_number` for MAP 1; `<kind>_receipt_number` for tax) AND column J = expected payment amount (gross_fee for one-time / gross_fee/4 for Quarterly / retainer amount for tax). Columns K+L+M+N+O must sum exactly to column J for Tracy's-verified gate to pass. If any check fails, the handler returns `pending: true` and the daily sweep retries. Advisor onboarding does NOT touch Tracy's sheet — all advisor-created members default to Money Mapping. PIP Meetings revshare ALSO does NOT touch Tracy's sheet — `pip_purchase_member_share` and `pip_purchase_vfos_share` are admin-entered at form-submit time and trusted as-is.

**27. Money Mapping member email banner shows the share amount.** Both MAP 1 (`actions/pipeline/contract-revshare.ts`), tax (`actions/tax/revshare.ts`), and PIP (`actions/msm/pip-revshare.ts`) render the Money Mapping confirmation banner with the same dark-blue (`#00488d`) solid background, white text, label-and-amount two-row stack as the Revenue Share banner — only the label differs ("Allocated to Money Mapping" vs "Your revenue share"). Don't revert to the lighter-styled label-only banner pattern.

**28. PostgREST `.neq('col', value)` excludes NULL rows.** A query like `.neq('payment_status', 'succeeded')` will NOT return rows where `payment_status IS NULL` — which is the common case for unpaid records. To match both NULL and non-succeeded values use: `.or('payment_status.is.null,payment_status.neq.succeeded')`. This bit the advisor sweep payment-stall query during Phase 6 testing — no rows matched until the filter was fixed.

**29. Onboarding-created advisor attributes (numbering now via #48).** Members created via `automation_ADVISOR_createmember` (Stage 3 button) are `member_type='Implementation'`, `elite_status='Active'`, `advisor_model='New Model'`, `member_category='advisor'`, `revenue_decision='Money Mapping'`, and `members.onboarding_id` = the `advisor_onboarding.id` FK (`ON DELETE SET NULL`). **The old fixed `>= 60100` member-number scan is GONE** — numbers are now assigned by the category-relative helper `nextMemberNumber('advisor','New Model')` (see #48). Manual Add Advisor form rows take whichever `advisor_model` the admin picks (required radio, no default — Legacy Model / New Model). The legacy existing members were backfilled to `advisor_model='Legacy Model'` in migration `members_advisor_model_column`, then to `member_category='advisor'` in `add_member_category`.

**30. `callApi` retry rule: reads retry once on timeout, writes never.** The frontend `src/lib/api.js` enforces a **20-second `AbortController` timeout** on every fetch. On timeout: actions matching `^load_|_load(_|$)` (plus the explicit `vault_list`) silently retry once after a 1-second pause — they're idempotent reads, so a duplicate request is harmless and a retry usually catches a now-warm edge function. All other actions throw `"Request timed out after 20s. Please try again."` immediately, because the server may have already processed the request and a blind retry could double-write (this exact bug created 2 CIQ rows from one click during a cold start before the fix). Non-timeout failures with `res === null` (network blip, CORS, offline) still retry up to 3 times with 2-second gaps — unchanged. If you add a new read action whose name doesn't match the regex (e.g., `get_*`, `fetch_*`), add it to the explicit allowlist in `isReadAction()`. NEVER add a write action to that list.

**31. Frontend caching layer in `src/lib/api.js`.** Module-level promise cache (NOT a React Context, NOT a state library — just `let cachedDataPromise` and a `Map` keyed by stringified payload). Two entry points: `loadCachedData()` for `load_data` (no key), `loadCachedAction(action, payload)` for keyed reads (currently wired for `msm_load_programs`, `msm_load_training_track`, `msm_load_client_track`). Subsequent calls within the same session return the original promise — instant. Cache invalidates on `clearSession` (logout) and exposes `clearCachedData()` / `clearActionCache(action?)` for explicit refresh. Failed promises auto-evict from the cache so retries can resolve. When adding caching for a new read, only do it for actions whose result is truly stable per-session (program structures, member rosters, etc.). Anything that mutates in-session (notifications, pipeline rows, plan progress) must NOT be cached or stale data will leak.

**32. Skeleton placeholder conventions** (`src/components/shared/Skeleton.jsx`). Building blocks: `Skeleton({width, height, style})`, `SkeletonRow({withPill, withDate})`, `SkeletonCard({rows, title})`, `SkeletonStats({count})`. Two rules guide what to skeleton: **(a)** for **conditional sections** (Stripe card, certs, notes — exist or don't per record), do NOT skeleton — the page should only grow as data lands, never shrink. **(b)** for **lists with unknown count** (CIQ rows, tax plans, history rows — section always exists but count varies), show **2-3 placeholder rows by default** — communicates "loading some list" without misleading on the count. Always wrap the skeleton in the same outer container (max-width, padding) as the loaded content so chrome doesn't shift. Header chrome (page title, tabs, back button) renders immediately and is NOT inside the skeleton — only the content area swaps. Pulse animation lives in `src/index.css` (`.vfo-skeleton` class + `vfo-skeleton-pulse` keyframes).

**33. Pass `enrollment_id` via `location.state` when navigating from a program-specific client list.** A client can be enrolled in multiple programs (Holistic + Tax). When a member clicks a client from the Tax Planning view, the click handler must pass `enrollment_id` via `navigate('/member/client/${id}', { state: { enrollment_id: enrollment.id } })`. Otherwise `ClientDetail` falls back to `client.enrollment_id` (the primary enrollment, usually Holistic) and renders the wrong program's tabs. Already wired in `MemberMSMTracking.jsx`; `msm_load_client_home` accepts the param and picks the correct enrollment server-side. Admin side uses a different navigation pattern and was confirmed clean.

**34. GitHub Pages browser-HTML cache after `npm run deploy`.** Even after the gh-pages push succeeds and the CDN is updated (verify by curling the live URL and checking the bundle filename in `<script>` / `<link>` tags), users will often see the OLD bundle for a few minutes because their browser cached the `index.html`. Plain Ctrl+Shift+R doesn't always evict the HTML cache. The reliable fixes are: (1) DevTools → Network → "Disable cache" checkbox → reload, (2) incognito window, or (3) wait 5-10 minutes for the browser's own HTML revalidation. Don't conclude the deploy "didn't work" if the live HTML serves the new bundle but the user's browser still shows old content — that's local cache, not deploy failure.

**35. PIP Meetings diverges from MAP1/Tax/Advisor in three ways.** (a) **No Tracy's-sheet verification** — `pip_purchase_member_share` and `pip_purchase_vfos_share` are entered by the admin in the Phase 3 form and trusted as-is; `automation_PIP_revshare` does a Stripe Connect transfer for `pip_purchase_member_share` directly (or Money Mapping no-op). (b) **No retry sweep** — there's no `pip_revshare_sweep` cron; failed transfers leave `pip_rev_share_status='Pending'` and need manual re-fire via service-role HTTP to `automation_PIP_revshare`. (c) **Reuses MAP 1 sandbox config** — no separate `'PIP'` row in `pipeline_sandbox_config`. PIP also unlocks locked child meetings on Additional PIP revshare success: `UPDATE client_priority_tracks SET pip_paid=true WHERE pip_purchased_from_track_id=<source>`.

**36. Docs/ exist in both main checkout AND every worktree.** Path guardrail applies to docs too — `C:\vfo-react\docs\...` is the main checkout (forbidden for Edit/Write); the worktree copy is `C:\vfo-react\.claude\worktrees\<branch>\docs\...`. Easy to slip on because docs feel "shared" and the Read tool happily reads either path. If you accidentally edit the main copy: `cd C:\vfo-react; git checkout -- docs/<file>` to revert, then re-apply via the worktree path. Git status in BOTH locations should be checked before commit.

**37. `CREATE TABLE LIKE … INCLUDING ALL` preserves column names verbatim.** When cloning `advisor_onboarding` → `accountant_onboarding` for the accountant onboarding pipeline, the column `agreement_signed_by_advisor_at` was carried into the new table unchanged. Backend code wrote to `agreement_signed_by_accountant_at` (after a global token swap) and would have crashed silently the first time an accountant signed. The fix: explicit `ALTER TABLE accountant_onboarding RENAME COLUMN agreement_signed_by_advisor_at TO agreement_signed_by_accountant_at`. Lesson: after a `LIKE INCLUDING ALL` clone, audit columns whose names embed the source table's domain and rename them to match the new domain. (Also relevant: `LIKE INCLUDING ALL` carries the SAME column-default expression, including any reference to the SOURCE sequence — create a new sequence + `ALTER COLUMN id SET DEFAULT nextval('<new_seq>')` after the clone or both tables will share PK space.)

**38. BoldSign field-read parser: be permissive and soft-fail.** The advisor `ceo-countersign.ts` handler had a latent bug since launch: `propData.signerDetails.find(s => s.order === 1)` never matched because BoldSign's actual key is something else (we don't know what — `signerOrder` also didn't match). Every advisor onboarding silently wrote `selected_*=false, payment_amount=0`, and the downstream `_stripecustomer` chain 400'd on the `payment_amount <= 0` guard. The fix that ships: try multiple position-key variants (`signerOrder` / `order` / `signer_order`) AND fall back to `signerDetails[0]`, multi-key field-id matching (`id` / `fieldId` / `name` / `label`), multi-value truthy check (`value` / `checked` / `selected`, with `"on"` / `"true"` / `true` / `"checked"` / `"Checked"` / `1` / `"1"` as truthy). If after all that nothing is detected, insert an admin notification with `recipient: 'admin'` + diagnostic shape dump (`Object.keys(propData)`, signerKeys, fieldKeys), and **continue to send Anton's countersign Gmail** — never block on the read failure. Downstream `_stripecustomer` still has its `payment_amount > 0` guard as the safety net. Same pattern applied to `accountant/ceo-countersign.ts`. Lesson: when parsing third-party API responses, fall back through plausible key names, surface failures loudly to admin, and never silently halt a user-visible flow.

**39. `member_logins` is one-row-per-email.** The `load-login-setup.ts` handlers (advisor + accountant) check `member_logins` by email and return `state: 'already_setup'` if a row exists for that email. If two onboarding rows (advisor + accountant, or just two accountants) share an email, the second one's setup page will refuse to issue a fresh passcode. During testing this can manifest as "Login Already Set Up" or (if the test email had a stale row from a prior delete-and-retry cycle) "Invalid setup link". Easy unblock for testing: `DELETE FROM member_logins WHERE LOWER(email)=...` (or change the onboarding row's email). In production, this is the right behavior — one human = one portal login.

**40. Login-setup chain is idempotent on `login_setup_email_sent_at`.** `automation_*_createmember` checks `if (ob.login_setup_email_sent_at) return` before firing `_loginsetupemail`. When you partially reset an onboarding row for retesting (e.g. NULL out `member_number` + `member_created_at` but leave the login-setup columns), the next Create button fires create-member, hits the idempotent "already created" branch (because `ob.member_number` is set by the retry), then `ensureLoginSetupAndFireEmail` short-circuits because `login_setup_email_sent_at` is still set. No new email goes out, and the old email's token points at the deleted member. To force a fresh login-setup email on the new member, also NULL `login_setup_token` + `login_setup_token_expires_at` + `login_setup_email_sent_at`, then either re-click Create or fire `automation_*_loginsetupemail` directly via service-role HTTP.

**41. Accountant attributes (numbering + classification now via #48 — the accountant-only filter is GONE).** The old `ACCOUNTANT_TYPES` heuristic and the `[30000,90000)` / `[90000,∞)` fixed ranges (and the 59526-collision they caused) are **removed** — replaced by the durable `member_category` tag + `nextMemberNumber('accountant', <model>)` (see #48). Accountant-onboarding-created members are `member_type='Implementation'`, `advisor_model='New Model'`, `member_category='accountant'`, and do NOT receive a `revenue_decision` (accountants don't have one — confirmed user-facing). The hardcoded `ACCOUNTANT_TYPES` list was deleted from `actions/accountant/create-member.ts`; the frontend `MembersPanel.jsx` keeps the list ONLY as the Add-Accountant Member-Type dropdown options, never for classification.

**42. `document_numbers` table needs a per-pipeline FK column per onboarding type.** The handler `actions/accountant/invoice-receipt.ts` (cloned from advisor) inserted into `document_numbers` with an `accountant_onboarding_id` column reference. The column didn't exist (the table only had `client_id` and `advisor_onboarding_id`), so the insert failed silently in supabase-js (no exception propagation). The receipt/invoice number was still written back to `accountant_onboarding.invoice_number` from the same handler, so the user saw a number but the `document_numbers` tracking row was missing — meaning the next invoice could re-use the same sequence number. The fix: explicit `ALTER TABLE document_numbers ADD COLUMN accountant_onboarding_id bigint REFERENCES accountant_onboarding(id) ON DELETE SET NULL`. Lesson: any new onboarding pipeline that uses `document_numbers` for tracking needs its OWN FK column added — don't assume the clone migration carried it.

**43. `MemberSetupPage.jsx` falls through advisor → accountant token lookup.** The `/member-setup?token=...` page is shared between advisor + accountant onboarding flows. The page tries `automation_ADVISOR_loadloginsetup` first; on `state: 'invalid'` it falls through to `automation_ACCOUNTANT_loadloginsetup`. It remembers which pipeline matched in local state and fires the matching submit action (`automation_*_submitloginsetup`). One shared page, two backends — no need to clone the page per pipeline. If a future onboarding pipeline (e.g. specialist) ever needs a login-setup token, extend the same fallthrough.

**44. `MembersPanel.jsx` extracts `MemberDirectoryView` shared by Advisors + Accountants.** Both panels are now thin wrappers around a single `MemberDirectoryView` component (search + list + click-into-profile multi-tab).
