## 🔒 SECURITY INVARIANTS *(check on EVERY DB or handler change — these must NOT regress)*

Non-negotiables from the 2026-06-18 security remediation. Re-check any time you add a table, policy, handler, or function — do not let a new feature quietly undo these:

1. **Every new public table = RLS deny-all + verify.** Create it with `enable row level security` + `create policy "Deny all access" … for all to public using (false)` in the SAME migration, then confirm with an anon-key probe (`curl --head -H "apikey:<anon>" -H "Authorization:Bearer <anon>" -H "Prefer:count=exact" "<base>/rest/v1/<table>?select=*"` → must be `Content-Range: */0`). The anon key is PUBLIC and `anon`/`authenticated` hold full table grants, so RLS is the ONLY thing protecting the DB. (gotcha #141)
2. **Every member-facing AUTH handler = caller-ownership check on `auth.callerMemberNumber`, NEVER a body id.** The edge fn runs as service-role (bypasses RLS), so a handler that reads/writes by a body `client_id`/`ciq_id`/`enrollment_id` without re-checking ownership is an IDOR. Reuse `utils/client-ownership.ts` (`denyIfNotOwnClient`/`denyIfNotOwnEnrollment`) + `actions/ciq/shared.ts denyIfNotOwnCiq`. Role-gates are deny-by-OMISSION + matched by EXACT action name. (gotcha #142)
3. **Every new SECURITY DEFINER function = pin `search_path` + `REVOKE EXECUTE … FROM public`.** (gotcha #143)
4. **After ANY DB/table/policy/function change → run the Supabase security advisor (`get_advisors`, type `security`) and confirm it's GREEN** — this is the automated net that catches a regressed (anon-reachable) table before it ships. It is part of the VERIFICATION GATE below.

Full audit history + live-verified detail: the 2026-06-18 security-remediation entry in [CHANGELOG.md](CHANGELOG.md) + gotchas #141–#146.

## ENVIRONMENT GOTCHAS

- **Bash is NOT on PATH** — use PowerShell. `git`, `curl`, `docker`, `psql` all run via PowerShell or `docker exec`.
- **PowerShell does NOT have `tail`** — use `Select-Object -Last N` instead. `| tail -3` will silently break pipelines (the upstream command may not run at all, swallowing output).
- **PowerShell mangles JSON inline** — use `--data-binary @file`:
  ```
  '{"action":"foo","x":"y"}' | Out-File tmp.json -Encoding ascii -NoNewline
  curl.exe -s -X POST <url> -H 'Content-Type: application/json' --data-binary "@tmp.json"
  Remove-Item tmp.json
  ```
- **PowerShell `Set-Content -Encoding utf8` AND `Out-File -Encoding utf8` both write a UTF-8 BOM** which leaks into commit message subjects (rendered as `﻿` in `git log`) and corrupts box-drawing characters. For bulk file writes AND commit messages:
  ```powershell
  $utf8 = New-Object System.Text.UTF8Encoding $false
  [System.IO.File]::WriteAllText($file, $content, $utf8)
  ```
- The Edit tool handles UTF-8 correctly — prefer it for moderate edits.
- **PowerShell here-string commit messages** can break on quoted text — use `git commit -F <tmpfile>` instead of inline `git commit -m`. AND write the tmpfile BOM-free per the above. The Bash tool's `cat > file << 'EOF'` heredoc avoids this entirely if you're already in a Bash context.
- **`git log --format=%B` in PowerShell collapses newlines into spaces** when piped through a variable — multi-line commit bodies become one long line. If you need to round-trip a message (e.g. to amend), rewrite the original from your prepared text rather than reading it back.
- **Supabase CLI stderr noise** (Bundling Function: …, Setting up Edge Functions runtime…) is benign — PowerShell flags it as RemoteException but it's normal CLI progress.
- **`vite build` stderr noise** (the `[plugin builtin:vite-reporter]` chunk-size warning) is similarly benign — PowerShell flags as RemoteException but the build succeeded. Look for `Published` at the end of `npm run deploy` output to confirm gh-pages push worked.
- **Local DB seed is sparse** — members table for TEST-001 doesn't exist; clients/pipeline_map1/email_templates start empty. Many "save didn't persist" reports are FK-driven seed gaps, not refactor regressions. See `supabase/seed.sql` for what IS seeded.
- **Local DB sequence gap** — `experts.id` has no DEFAULT in the pg_dump baseline; inserts via `save_specialist` against the local DB fail with not-null violation. Pre-existing test-data issue. (Frontend works around it by computing id client-side.)
- **CORS in local-dev** — Kong gateway intercepts OPTIONS preflight and stamps `Access-Control-Allow-Origin: *`. Production hits the function directly. Don't worry if local CORS smoke shows `*`.
- **`supabase/.temp/cli-latest` shows as modified after any CLI deploy** — Supabase CLI version-tracking artifact, not project code. Exclude from every commit.
- **GitHub Pages CDN + browser HTML cache** — after `npm run deploy` succeeds (look for `Published`), the live bundle filenames change (e.g. `index-<hash>.js`), but browsers often serve a cached `index.html` that points at the OLD bundle. Confirm the deploy reached the CDN by `curl -s https://jlathamert.github.io/vfo-portal/ | grep -oE 'index-[A-Za-z0-9_-]+\.(js|css)'` and comparing to the new filename in the build output. If the live HTML serves the new bundle but the user's browser still shows old content, it's local cache — DevTools → Network → "Disable cache" → reload, or use incognito.

## SESSION-LEARNED GOTCHAS

The **full numbered registry (#1–#172)** lives in **[GOTCHAS.md](GOTCHAS.md)** — read on demand. Numbers are permanent and referenced as `#N` across the docs; never renumber, and add new gotchas there (incrementing from #172). Below is only the curated **ALWAYS-APPLIES** subset — the invariants that bear on most work. A `see #N` reference resolves to the full entry in GOTCHAS.md.

**Deploy / build / ops**
- **#10** — `boldsign-webhook` deploy needs `--no-verify-jwt` every time (else BoldSign gets 401).
- **#74 / #112** — local `deno check` writes a v5 `deno.lock` the Supabase CLI bundler rejects; use `--no-lock` + `rm -f deno.lock` before `supabase functions deploy`.
- **#134** — JSX must live in a `.jsx` file; the `vite build` / `npm run deploy` rollup build rejects JSX in a `.js` file (the dev server tolerates it).
- **#145** — production deploys (`supabase functions deploy` / `npm run deploy`) need an EXPLICIT "deploy"; ambiguous approvals ("continue"/"yes") are blocked.
- **#146** — the Bash tool's cwd PERSISTS across calls — `cd` to the correct repo/worktree (or use absolute paths) immediately before a deploy.

**Auth / security invariants** *(see also the SECURITY INVARIANTS box above)*
- **#141** — every new public table = RLS enabled + a `"Deny all access" USING(false)` policy in the SAME migration, then verify with an anon-key REST probe.
- **#142** — service-role bypasses RLS → authorization is 100% app-layer; member-facing AUTH handlers MUST re-check ownership against `auth.callerMemberNumber`, never a body id.
- **#143** — new SECURITY DEFINER function = pin `search_path` + `REVOKE EXECUTE … FROM public` (revoking from anon/authenticated alone is not enough).
- **#11** — chain auth: a handler chaining to another AUTH handler must forward `body.token`, not just the `Authorization` header.
- **#144** — frontend `callApi` hard-redirects on ANY 401 except `LOGIN_ACTIONS`; add new login-type actions to that allowlist.
- **#171** — Lost/Removed members are BLOCKED at `member_login` (403 after passcode verify); never delete `member_logins` rows to revoke access — flip `elite_status` instead, and remember the shared Test Member must stay Active for the test login to work.
- **#167** — the Accounting / Automation / Member Overview tabs are per-admin tab-gated via `allowed_admins.allowed_tabs` (NOT superadmin-only anymore); a NEW action behind one of them MUST be added to `TAB_ACTIONS[...]` in `role-gates.ts` or a granted non-superadmin admin gets 403. Grants apply on the admin's next login (session-stamped).

**Backend data patterns**
- **#28** — PostgREST `.neq('col', v)` EXCLUDES NULL rows; use `.or('col.is.null,col.neq.v')`.
- **#84** — Storage writes from the edge fn MUST use the supabase-js storage client, not a hand-rolled `Authorization: Bearer <SERVICE_ROLE_KEY>`.
- **#92** — allocate INV/REC numbers via collision-safe `utils/doc-numbers.ts allocateDocNumber()`; never revert to insert-once.
- **#45** — `deno check` baseline = 0; any error = fail (the VERIFICATION GATE depends on this).
- **#155** — `members.member_category` + `member_number_baselines` both carry CHECK constraints (advisor/accountant only); a new category needs the `members` CHECK widened and its numbering baseline kept as a code constant, not a baselines row.

**Stripe / payments**
- **#13** — the Stripe webhook routes by `metadata.pipeline` + `metadata.payment_kind`; set both on every Checkout / PaymentIntent you create.
- **#15** — Stripe idempotency keys must auto-rotate per retry attempt, not be reused.
- **#159** — before a Stripe Connect transfer, verify the destination's `capabilities.transfers === 'active'`; a created-but-unonboarded account rejects transfers — treat it as "awaiting setup" (resend link), not a failure. A feature's Connect accounts + transfers must run in the SAME sandbox/live mode.

- **#18** — notification `link` must be a real frontend route (e.g. `/admin/client/<id>?tab=tax`), or the bell click bounces to login.
